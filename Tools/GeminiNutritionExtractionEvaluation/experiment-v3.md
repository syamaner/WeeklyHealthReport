# Candidate v3: evidence binding and record resolution

Architecture gate: the application adapter owns selected-source identity and content hashes. The model owns only extracted fields and evidence locations. A frozen request envelope binds the exact evidence text, selected source and request bytes. Responses are validated against a schema without a model-writable source URL; orchestration adds source metadata from that envelope. A supplied conflicting/extra source field is rejected, never used to replace selected evidence. Keep raw model extraction separately for audit. This is an eval harness, not an app admission change.

Discovered record IDs are untrusted leads. A pure resolver requires an exact ID and identity/preparation match against the existing admitted local release, then checks every claimed nutrient value/unit against that record. It can confirm a record, flag conflicting claims, or leave the lead unresolved. Citation titles and model-written URLs are not proof. No fuzzy substitution, new source admission or implicit user confirmation. The infrastructure adapter reads only the pinned local CoFID/USDA resource versions; domain policy has no network/filesystem dependencies.

Freeze before calls: unchanged v1 gold, v3 extraction prompt/schema, binder, resolver, collector, scorer dependencies, source text manifest and record-resolution fixtures. Run 20 development extraction requests, no retries, plus offline resolution of the four leads observed in v2. Preserve v1/v2 results. A source-bound result is reported under v3, never as a repaired v2 score. Claims of a complete workflow require both verified selected evidence and supported quantities; safe refusal on an unresolved lead is not successful discovery coverage.

If all development extraction and evidence checks pass, select this exact candidate before running the four reserved holdout cases once in supplied-panel mode. This first holdout assesses extraction and binding, not previously untested holdout-site fetching. Maximum this turn: 24 provider POSTs (20 development, conditional 4 holdout). No new discovery calls or prompt tuning after holdout. Failures remain failures. Source/candidate confirmation in this harness is simulated evaluation state and does not authorise saving a real food entry.
