# Direct edible weight: quantity declaration contract v1

Issue #166. Baseline: main `fc31c355f7dd29a0690b8e4a950969fd3b0477ab` after PRs #167, #168 and #169. Software implementation only; physical acceptance remains outstanding.

## Behaviour and responsibilities

`Enter measured weight` starts a separate, empty gram field and an explicit measured/estimated choice. It never relabels an original count or volume as grams, including `2 eggs` and `200ml whole milk`. Original input and capture evidence remain separate. Existing typed grams are not evidence of measurement. Without this new path, legacy gram, volume and manual count conversions keep their existing meaning; old records have no declaration.

The amount is food as eaten in the selected preparation: exclude shell, peel, bone and uneaten parts. Do not substitute raw composition, infer density or portion weights, or infer added/absorbed oil. In food-only/tared mode, the gram field is the edible total. In plate mode, its label explicitly changes to the gross food-and-plate weight; the stored declaration retains that scale total, and the referenced immutable plate version determines the net edible grams. Saving, preview and reopened entries share the same pure quantity calculation.

Changing count does not replace an entered gram total. Candidate changes reset acceptance; preparation/identity changes require reconfirmation of the retained total before saving. No guide estimates or source-backed size selector are admitted by this change. Invalid, non-finite or absent gram totals, an absent measured/estimated choice, invalid original input, missing acceptance and unsupported plate combinations block saving with a field-local recovery action. The optional original field can be cleared or corrected independently.

Domain types hold the versioned declaration and validate the relation between declared total, plate and edible quantity. Application state owns entry/reconfirmation and calculation orchestration. Presentation owns field labels and recovery wording. The constructor/decoder rejects context-free declaration inconsistencies; stored reads, integrity checks and application reopen also validate plate-dependent totals. The existing in-memory and GRDB adapters both enforce the same declaration invariant, resolving a new plate from the transaction before consulting stored records. No new infrastructure interface or universal metric framework is introduced.

## Immutable persistence and compatibility

`LogItemVersion.weightDeclaration` is optional. Its v1 declaration records `measured` or `estimated`, the gram scale total and optional original input. A missing declaration means legacy unspecified; it is omitted when encoding, preserving old canonical bytes. Removal/restoration and nutrition re-resolution retain this metadata. New direct-weight entries use `confirm_food_v2`; other log-writing operation families have explicit v2 payload types when carrying declarations. Registry v3 accepts historical operation types and the new types. Metadata under old operation contracts and unknown types/versions is rejected. The unsigned ledger operation schema and historical payload/hash calculation remain unchanged.

The archive food contract advances from v2 to v3. Manifest/projection v1 and v2 still verify under their original contract and canonical bytes, without filling in invented declaration metadata. New declaration metadata requires v3. The SQLite schema identity also advances to v3 through a marker-only migration; no immutable payload or operation bytes are rewritten. Older binaries reject the future store version. The unsigned ledger operation schema, backup container format and daily projection schema remain unchanged. Old clients cannot accept v3 as an old contract.

`food-intake-summary-v2` carries estimated quantity provenance into the existing estimate indicator. Its numerical scaling is unchanged. User-estimated weight keeps consumed results labelled estimated even for exact package nutrients; user-measured weight does not upgrade augmented source nutrients.

## Manual device acceptance

1. Search `200ml whole milk`, choose the intended per-100-g record and open direct weight entry. Verify the original 200 mL is retained, the gram field starts empty, and saving requires both a positive gram total and an explicit basis. Enter a user-reported measurement; confirm reference nutrition retains the source basis and consumed values use the separate gram total.
2. Search `2 eggs`, select the intended cooked preparation, then enter the total weighed after peeling/cooking. Change the count to 3: the gram total must stay unchanged. Switch candidate/preparation and verify acceptance resets and the retained total must be checked again. No size, raw-record substitution or inferred oil is offered.
3. Try a user-entered estimate with exact package nutrients and a measured quantity with generic estimated nutrients. Both consumed displays retain the appropriate estimate indicator.
4. In food-only and gross plate modes, check the field labels, net consumed amount and save/reopen values. Try an empty/missing plate, plate heavier than total, invalid original input and invalid gram total; verify recovery appears beside the relevant field.
5. Save and reopen measured and estimated entries, then export/import the local archive using synthetic data first. Verify original input, preparation, source, scale total, net edible amount and declaration survive.

Simulator/package/static-analysis evidence does not establish representative physical usability or HealthKit acceptance. No provider calls, source adoption, HealthKit writes, phone control or TestFlight upload are included.
