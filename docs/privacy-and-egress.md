# Privacy and data egress

This is the single engineering list of what may leave the device, where it goes and which contract governs it. The user-facing statement is [`privacy-policy.txt`](privacy-policy.txt); keep both consistent. Anything not listed here must not leave the device.

## Stays on the device unless the user sends it

- **HealthKit data** leaves only inside a Daily JSON export the user reviews and sends, or a report or Today screen the user copies, shares or screenshots (including the today-so-far Health values in Today's Full Page). Individual glucose readings (each visible reading for the selected day with its time, value, source name and source bundle identifier) are in that export only while the user keeps Glucose readings on, which is off by default ([glucose-readings-export-contract-v1.md](glucose-readings-export-contract-v1.md), owner-approved terms E1 to E4, 11 November 2026). They are part of that file wherever the user takes it, including View exact file and its Copy JSON, which copies the exact text to this iPhone's clipboard only, where it expires after ten minutes ([daily-export-contract.md](daily-export-contract.md)). Developer tools shows each glucose source's name and bundle identifier, the reading count, the first and last reading time and the most common interval between readings of the prepared file, never a reading value. The readings are not on the Health screen, in Copy all or in Full Page.
- **Notes** leave only inside the Daily JSON export for their day. Today's Full Page shows only today's note count, never note text.
- **The food log** for one selected day leaves only inside the separate food daily export file the user reviews and sends to Google Drive ([food-daily-export-contract-v1.md](food-daily-export-contract-v1.md)); the health Daily JSON export never contains it. Otherwise the food log, intake history, saved foods, favourites, drafts and inventory stay local, except an inventory backup file the user explicitly exports to a location they choose, and Today's Full Page when the user takes a screenshot and chooses Full Page: it contains today's food totals and quick-add favourite names and default amounts. The Health report's Copy all and Full Page contain the Food and water section's logged-day counts and averages ([health-food-and-water-v1.md](health-food-and-water-v1.md)). HealthKit food writes remain a separate plan (#97).
- **Audio** never leaves. Speech recognition is on-device only.
- **Label photos** leave only as the single prepared image sent when the user taps Read label with AI. The image kept with a logged entry stays on the device; it is not in the Drive food export or backups. A label photo may be taken with the camera, chosen from the photo library, or pasted with the system paste control on the Nutrition label screen, which reads the clipboard only when tapped; pasted label text is read on the device and never sent. The clipboard is a source here, not a destination (#454, owner decisions Q1 to Q3, 10 November 2026).

HealthKit access is read-only: authorisation `toShare` stays empty. No analytics, tracking, crash SDK, backend, account system or background delivery.

Source datasets bundled with the app (CoFID 2021, USDA FoodData Central, TFDA and Ciqual 2025) are downloaded by a developer, outside the app, before the projection is built. That download carries no user data and is not app egress; the app reads only the bundled, hash-checked projections and makes no request to those publishers. Owner approval: 4 November 2026, on #384 ([ciqual-2025-admission-v1.md](ciqual-2025-admission-v1.md) section 1.3).

Developer tooling for Your food database ([personal-food-catalogue-import-v1.md](personal-food-catalogue-import-v1.md)) runs on the owner's Mac, not in the app, and is not app egress. Its scripts send to Open Food Facts only (a) product titles from the owner's own receipts and from intake items that name a brand, with pack sizes removed, (b) generic food names, and (c) barcodes of chosen matches. They never send receipt text, notes, amounts, prices, addresses or identifiers, and all requests go through the skill's paced client (below the published limit, with backoff and Retry-After). Receipt titles come only from receipt item lines, never headers, after the extractor's privacy gate, and every query also passes an outbound gate (no currency, prices, emails, postcodes, long numbers, honorific names, street addresses or order and payment words, and at least one known food word, or Chinese text containing a known Chinese food fragment). Because a word list cannot recognise every personal name, no search query is sent until the owner has approved that exact query: the scripts list every planned query in a pending file and stop before any network call, then send only approved queries and never declined ones. Barcode lookups for chosen products send only digits taken from Open Food Facts' own results and need no separate approval. A product page the owner names is read once with the agent's web-fetch tool. What the agent reads reaches the agent's model provider: the owner's notes, label and receipt photos, CSV header rows, product pages the owner names, and the food titles the agent maps or shows the owner for approval; only when the owner asks. The agent may also use its web search tool to enrich nutrient values, only when the owner has asked for it in that session. Each query is a food description (title, brand, variety, state), never text from receipts, notes or photos, and is either a generic food name with no brand or a query the owner has approved exactly, for web search, before it is sent; approval of an Open Food Facts query does not extend to web search. A value read from a result page keeps the page address, the date read and the state it describes in the private working catalogue, and stays unconfirmed until the owner confirms it. Owner approval: 7 November 2026; web search 8 November 2026.

Developer tooling for the pasted-label AI text evaluation ([pasted-label-ai-text-v1.md](pasted-label-ai-text-v1.md) sections 5.2 and 10, #416) runs on the owner's Mac, not in the app, and is not app egress. The tool (`Tools/PastedLabelAITextEval`) sends to `https://openrouter.ai/api/v1/chat/completions` only, plus keyless GETs of OpenRouter's model endpoint and zero-data-retention listings (T1). Each request carries one evaluation label's pasted text exactly as saved, the fixed instruction and the fixed output schema, and nothing else: no name, owner data, health data or identifiers (T2). The texts are the nutrition sections of public product pages. Every request pins one zero-data-retention endpoint with `data_collection: "deny"` and `allow_fallbacks: false`, and a response whose model or provider differs from the request counts as failed (T3). The key is the OpenRouter key already approved for the photo evaluation, read from the `OPENROUTER_API_KEY` environment variable into memory only and never printed or stored (T4). Spend stops at $5 per matrix cell, $25 for the programme and $0.20 per call, enforced in the text evaluation's own spend ledger before every call (T5, D25, D26). A transient failure is retried at most twice more, with backoff that honours `Retry-After`, and every attempt is reserved in that ledger. Raw responses, the response cache and the ledger stay in the owner's private evaluation folder; the repository gets counts, versions and hashes only (T6). The sealed held-out set is sent once, by the frozen version (T7). promptfoo, which orchestrates the runs, is local tooling that adds no destination: it is pinned, installed without install scripts (D24), and run with telemetry, update checks and sharing switched off and its state outside the repository. Owner approval: 7 November 2026 (D6); this note was added on 8 November 2026, before the first run.

## Rules for every egress path

- User-initiated and visible; no automatic retries, pagination, per-keystroke requests or background work beyond the approved budget for that path. A path's contract may approve bounded retries of retryable transport failures within the one user action, with backoff that honours `Retry-After` and a whole-call deadline (label photo reading: 3 attempts in 90 s).
- User-owned credentials live in this-device-only Keychain storage and are never sent to third-party publishers.
- Responses are evidence for review, never authority: citations or model confidence alone never authorise nutrition or saving.
- Adding a destination, widening a payload or changing when a request happens needs a versioned contract, an update to this file and `privacy-policy.txt`, and explicit user approval. Prove a new transport with synthetic data before integrating it with HealthKit or any other personal data.

Evaluation best-estimate amendment (8 November 2026)

For the explicitly requested estimate review, food descriptions may be sent to web search and
source sites, with national composition databases and manufacturer pages preferred. Receipt text
and personal data are excluded. Source nutrient values, food state and provenance may enter the
model context for this work. This narrowly supersedes the earlier evaluation nutrient-context and
external-query exclusions. Private outputs retain source URL, date read and page_unconfirmed status;
no catalogue or evaluation file is published, and no app transfer or automatic food save is added.
